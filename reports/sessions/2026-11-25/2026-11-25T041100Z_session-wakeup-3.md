## New source-coverage finding

The current experiment calls the legacy Treasury Fiscal Data `/v1/accounting/od/auctions_query` endpoint. Its run manifest records 226 selected nominal 10-year auctions through 2026-10-07.

Treasury's current dataset page documents two distinct tables and endpoints:
- The legacy table remains available through the old `auctions_query` endpoint.
- The updated table uses `/v1/accounting/od/treasury_securities_auctions_v2` and contains post-migration records.
- Treasury says the new APIs contain data beginning 2026-10-01, historical data will be added later, and the old APIs are expected to remain available until spring 2027.
- The current page's old-table preview ends 2026-10-30, while the updated table covers November 2026 records. The official November refunding statement scheduled a 10-year note auction for 2026-11-10.

Sources:
- [Treasury auction dataset and table metadata](https://fiscaldata.treasury.gov/datasets/treasury-securities-auctions-data/treasury-securities-auctions-data)
- [Treasury auction API migration notice](https://fiscaldata.treasury.gov/featured-content/treasury-auctions-data-updates-enhancements/)
- [Official November 2026 refunding statement and 10-year auction date](https://home.treasury.gov/news/press-releases/sb0678/)

This means the current historical sample is not current through the intended 2026-11-24 cutoff: the November 10 auction is absent from the legacy-only extraction. The observed 226-row historical result must not be described as complete through November. This is a data-coverage defect, not evidence for or against the predictive hypothesis.

Treasury's updated schema uses fields such as `security_desc` and `comp_auction_close_date`; the legacy script expects fields such as `security_term`, `original_security_term`, and `auction_date`. A hybrid adapter therefore needs explicit, tested field mapping, result-field availability checks, CUSIP/date deduplication, and a cutoff-aware completeness check. Do not assume all required bidder-composition fields exist in the new table until verified.

The existing use of `record_date` as the publication date and the first yield observation strictly after it is conservative with respect to publication timing; retain that guard when integrating the updated table.
